1. WHAT IS THIS THING?

The parser engine, located in the package xmlFastParser, is a predictive, multi-threaded XML parsing library designed to process large XML files (and ZIP archives containing XML) based on a blueprint specification (.bp file). It was built specifically to support the XML2TXT conversion tool, but it is general enough that, with the proper handler registration and blueprint parsing logic, you could build a completely different application.

Note: You must not edit the parser engine files (xmlBluePrint.java, xmlBluePrintHolder.java, etc.) unless you have explicit authorization. They are complete.

2. FILE INVENTORY — EVERYTHING YOU NEED TO KNOW ABOUT EVERY FILE

2.1 xmlBluePrint.java

This is the heart of everything. It is a large file (thousands of lines). It contains:

  • State machine definitions for tag parsing, attribute parsing, value parsing, and closing tag handling.

  • Predictive parsing logic — it tries to predict the next tag from prior log data so it can jump forward instead of scanning byte-by-byte (case-sensitive by default, now normalized to uppercase).

  • Pipeline management — it manages a fixed-depth pipeline of job slots.

  • Thread management — it starts worker threads that read from pipeline slots and execute parsing.

  • Handler invocation — when a target node is reached, it calls registered handlers. 

// Basic initialization pattern
xmlBluePrint parser = new xmlBluePrint(safeMode);
parser.setPipeLineDeep(4);      // Slot count will be (2^4)-1 = 15
parser.setThreadCount(2);       // Two parser worker threads
parser.run();                   // Start engine; must have rootRegist first

2.2 xmlBluePrintHolder.java

Each worker thread has a holder object. The holder tracks:

  • pointer — current byte position in the job buffer.

  • jobStart, jobLength, inprogress — which pipeline slot is being processed.

  • currentNode, nextPredictTarget[], nextPredictDistance[], safeMode — predictive / safe parsing state.

  • logSize, hash — validation data for tags.

2.3 xmlBluePrintNode.java

Represents a node in the parsed tree. Has fields like tagHash, tagName, isTarget, path, and references to child nodes. When the parser encounters a tag that matches a registered entity path, it creates or updates a node and calls the registered handler.

2.4 xmlBluePrintCall.java

A call record that helps dispatch to the correct handler. It stores the path hash, handler reference, and context needed to invoke EventHandlers.HD_Entity or HD_Column.

2.5 CELL.java

A cell definition used in the blueprint to describe a column/field. Defines name, path, type, and relationship to parent entities.

Every time you change N, the total number of pipeline slots changes exponentially. This affects memory usage because each slot holds an XmlToken object with buffers. Do not blindly increase N because it feels like a good idea. Measure first.

Note: The pipeline is a circular/round-robin queue. pushJob() puts work in; pullJob() takes completed work out. If you fill faster than you drain, pipes fill. If you drain faster, you wait.

4. PREDICTIVE PARSING IN EXCRUCIATING DETAIL (v01.01.00)

The parser uses a predictive mechanism based on createPredictPath and verifyPrediction, not old nextPredictTarget. Constructor: public xmlBluePrint(boolean safe).

4.1 Predict&Jump — New Mechanism

Path creation: createPredictPath(root,true) builds nextPredictTarget[threadCount] and nextPredictDistance[threadCount] per target node.

Verify: verifyPrediction(holder) scans +/-5 from pointer + distance; finds <tag>; compares hash with nextPredictTarget.tagHash. If match → holder.jumped = true, holder.currentNode = nextPredictTarget, HD_TARGET_TAG. If mismatch → fallback to FSM (byte-by-byte).

SafeMode / No_Predict&Jump: When safeMode = true (via constructor or -safe), if (!holder.safeMode && verifyPrediction(holder)) return; skips jump entirely. On error in safeMode: EV_RESET_IN_SAFEMODE = 1004 via doSafeMode().

Success (predict): Distance + tag hash match → jump to target; skip repetitive scanning.

Failure / SafeMode: Hash mismatch or safe enabled → no jump; continue FSM; error triggers reset event 1004.

5. HANDLER REGISTRATION — EVERY PATTERN

You must register handlers before calling parser.run(). If you forget rootRegist, run() returns false and parsing fails.

// Root (mandatory)
parser.rootRegist(EventHandlers.HD_Root, tokenRoot);

// Error (mandatory for error reporting)
parser.errorRegist(EventHandlers.HD_Error, tokenRoot);

// Per-entity registration (from blueprint parsing)
for (TokenEntity entity : allTokenEntity.values()) {
  if (entity.path != null && entity.path.length() > 0) {
    parser.regist(entity.path, EventHandlers.HD_Entity, entity);
  }
  for (TokenColumn column : entity.AllTokebColumn.values()) {
    if (column.path != null && column.path.length() > 0) {
      parser.regist(column.path, EventHandlers.HD_Column, column);
    }
  }
}

The path is hashed using xmlBluePrint.hash(byte[], len). The parser compares hashes to determine if a tag matches a registered path. This is why paths must be registered with the exact byte sequence — even a minor character change produces a different hash and breaks matching.

6. TOKEN REUSE — HOW MAINLOOP WORKS (STEP BY STEP)

6.1 Phase 2a — Fill Pipeline

while (xmlRead < allXmlToken.length && (xml = source.getXml()) != null) {
  allXmlToken[xmlRead].xml = xml;
  parser.pushJob(xml.byteBuffer, xml.size, allXmlToken[xmlRead]);
  xmlRead++;
}

We fill as many pipeline slots as exist (up to allXmlToken.length, which is derived from parser.getPipeLineTotalSlot() = slot count = (2^N)-1). Each token carries its own XML package.

6.2 Phase 2b — Process Remaining Files

while ((xml = source.getXml()) != null) {
  // Wait for completed token
  while ((xmlToken = (XmlToken) parser.pullJob()) == null) {
    LockSupport.parkNanos(10_000_000L); // 10ms sleep
  }
  // Flush output
  flushXmlToken(xmlToken);
  // Close source XML
  source.closeXml(xmlToken.xml);
  // Reuse token with new XML
  xmlToken.xml = xml;
  parser.pushJob(xml.byteBuffer, xml.size, xmlToken);
  xmlRead++;
}

Performance warning: The 10ms park is a busy-wait with small sleep. If the parser is very fast, this is fine. If parser is slow, this wastes CPU. Consider adaptive sleeping or using a blocking queue instead.

6.3 Phase 2c — Drain Pipeline

while (xmlReturn < xmlRead) {
  while ((xmlToken = (XmlToken) parser.pullJob()) == null) {
    LockSupport.parkNanos(10_000_000L);
  }
  xmlReturn++;
  flushXmlToken(xmlToken);
  source.closeXml(xmlToken.xml);
}

This is where most of the time is spent on large datasets. After the last XML file is pushed, the pipeline still holds completed jobs that must be pulled and flushed. The flush writes to disk, which can be slow if output is large (e.g., 1.4 GB). This is why the total elapsed time can be much larger than the parser processing time.

7. FLUSH BEHAVIOR — DISK BOTTLENECK EXPLAINED

void flushXmlToken(XmlToken xmlToken) {
  if (xmlToken.msgError != null) {
    errorLogWriter.println(xmlToken.msgError);
  } else {
    for (Map.Entry<Long, String> entry : xmlToken.buffOP.entrySet()) {
      PrintWriter writer = allEntityOutput.get(entry.getKey());
      if (writer != null) {
        writer.println(entry.getValue());
        flushBatchCount++;
        if (flushBatchCount % BufferSize == 0) {
          writer.flush();
        }
      }
    }
  }
  xmlToken.msgError = null;
  xmlToken.buffOP.clear();
}

Key insight: Use Large Number of records flush also using a larger buffer, but can reduce I/O overhead significantly.

8. BLUEPRINT PARSING — BPParser

BPParser.parseBP(path, numThreads) reads the .bp file and produces a map of entities. Each entity has:

  • fileName — output file base name

  • path — XML path for entity

  • AllTokebColumn — map of columns (note the typo in source: Tokeb instead of Token)

  • hash — computed from fileName for writer lookup

The blueprint defines which XML tags correspond to which output entities and columns. You must create a valid BluPrint.bp for your data, or use the provided one in Lab/BluPrint.bp.

9. SOURCE HANDLER — READING ZIP AND XML

SourceHandler scans a folder (not subfolders) for files ending in .xml or .zip. For .zip, it opens entries and checks if the entry is an XML file. It then exposes getXml() which returns an XmlPackage containing the byte buffer, size, and filename.

Warning: Source folder is not scanned recursively. All files must be directly in -s folder.

10. ERROR HANDLING

Errors are captured in xmlToken.msgError and written to xml2txt.err in destination folder (append mode). The error log writer is created in BootUp and closed in ClosingJob.

11. COMPLETE REPRODUCTION STEPS (TO BUILD YOUR OWN)

  1. Copy xmlFastParser/ source files to your project.

  2. Write EventHandlers.java matching the handler signatures used by XML2TXT.

  3. Write SourceHandler.java that can open XML and ZIP files from a source folder.

  4. Write XML2TXT.java with BootUp (parse BP, register handlers, open writers), MainLoop (fill/drain pipeline, flush output), ClosingJob (close writers, rename files).

  5. Compile with javac -d compiled java/*.java java/xmlFastParser/*.java.

  6. Run with java -cp compiled XML2TXT -p Lab/BluPrint.bp -s Lab/datas -d out -t 2 -N 4.

  7. If output is large, expect long flush phases — this is disk I/O, not parser failure.

12. SUMMARY — EVERYTHING IN ONE SENTENCE

The parser takes XML from a source folder (direct or in ZIP), applies a blueprint to identify entities and columns, writes results to temporary _pending.txt files using per-entity writers with periodic disk flushes, then renames those files with timestamps upon shutdown — all while using predictive parsing and multi-threaded pipeline slots defined by (2^N)-1.
