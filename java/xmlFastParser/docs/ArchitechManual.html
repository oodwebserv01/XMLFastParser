xmlFastParser — Architecture Manual (Rebuild From Zero)

Purpose: This document describes every structural element, algorithmic trick, and design decision in the parser engine so that an AI (or human) can reconstruct an equivalent system without reading every source file. It covers the class model, pipeline math, predictive parsing mechanics, hash design, thread coordination, blueprint integration, and all optimization techniques.

Scope: Packages: xmlFastParser (engine) + java/XML2TXT (driver). Engine is immutable; driver uses engine.

1. High-Level System Design

The architecture is a three-phase pipeline with predictive parsing and thread-pooled workers:

  • BootUp — initialize parser, parse blueprint (.bp), register handlers, open output writers, allocate token array.
  • MainLoop — fill pipeline slots; pull completed jobs; flush to disk; reuse tokens with new XML.
  • ClosingJob — close writers; rename _pending.txt → timestamped; shutdown parser.

The parser itself is state-machine driven with a byte-level FSM that handles tag opening, attribute parsing, value accumulation, self-closing tags, closing tags, and namespace prefixes. It operates on byte arrays (not strings) for speed.

2. Class Catalog — Every Component

2.1 xmlBluePrint (Engine)

The core class. It contains:

  • Static hash methods — FNV-1a 64-bit hash over byte ranges; skips Clark notation namespace; normalizes a-z → A-Z.
  • Pipeline slot array — indexed by inprogress / pointer; managed via push/pull.
  • Worker threads — each tied to a xmlBluePrintHolder.
  • State machine — integer state codes for tag parsing (S_TAG, S_ATTR, S_VALUE, S_CLOSE, etc.).
  • Predictive log — predictedLog / predictedIndex used for jump-ahead.
  • Handler dispatch — rootRegist / errorRegist / regist by path hash.

2.3 xmlBluePrintNode (Tree Node)

Represents an XML element node with:

  • tagHash — hash of tag name
  • tagName — string or byte range of tag
  • isTarget — whether this path is registered
  • path — registered path for handler lookup
  • children / parent — tree links

2.4 xmlBluePrintCall (Dispatch Record)

Stores the handler reference, path hash, and calling context so that when parser reaches a target node it can invoke the correct static method (HD_Entity, HD_Column, etc.).

2.5 CELL (Column Definition)

Used by BPParser to define output columns: name, path, data type, and relationship to parent entity.

Design choice: Exponential slots allow deeper pipelines with fewer workers, but memory usage grows because each slot holds full XmlToken buffers. Use the smallest N that meets throughput needs.

4. Hash Function Design (FNV-1a, Case-Normalized)

The hash is a 64-bit FNV-1a over byte arrays. Key techniques:

  • Offset basis: 0xCBF29CE484222325L
  • Prime multiplier: 0x100000001B3L (FNV-1a standard)
  • Namespace skip: If byte } found, start hashing after it (Clark notation {uri}local).
  • Prefix skip: Before hash start, skip any prefix before : if present.
  • Case normalization: a-z → A-Z (byte -32) so /a/b and /A/B match.

This means registration paths must match the local name after namespace, and case differences are ignored — a deliberate simplification for unstable XML sources.

5. Predictive Parsing — The Key Speed Trick

The parser tries to avoid scanning every byte by maintaining a predicted log — a history of previous tag hashes at offsets. When parsing reaches a point where a tag is expected, it calculates the best match from the log and attempts to jump to that offset.

5.1 Prediction Lifecycle

  1. Init: Build best-match from log history (predictedIndex, predictedLog).
  2. Activate: Set predictionActive = true.
  3. Jump: Set pointer to predicted offset; verify expected hash.
  4. Success: Continue from new position; save faster path.
  5. Failure: Restore originalPointer; set predictionActive = false; fall back to byte-by-byte.
Why it works: XML is highly repetitive. If you just closed <item>, the next opening tag is likely <item> again. The prediction avoids scanning hundreds of bytes to confirm.
Risk: Malformed or irregular XML causes frequent restoration; overhead can exceed savings. The parser handles this automatically but performance degrades.

7. Thread Model — How Workers Collaborate

Parser creates threadCount workers. Each worker pulls from a shared pipeline via pushJob / pullJob. The main thread (MainLoop) pushes new jobs and pulls completed ones — so parsing is parallel but flush/IO is serial.

Trick: Because flush is single-threaded, increasing parser thread count only helps if the bottleneck is parsing, not disk. With large outputs, disk flush dominates (as observed: 250 rows sweet spot).

8. Blueprint Integration (BPParser)

The blueprint (.bp) defines entities and columns. BPParser.parseBP() produces:

  • HashMap<Long, TokenEntity> — entities keyed by fileName hash
  • Each TokenEntity has path, AllTokebColumn, fileName
  • Columns defined via TokenColumn with path, name

Registration uses these paths — the parser does not know about entities until registered.

9. SourceHandler — Input Abstraction

Reads folder contents (non-recursive). For .zip, opens entries; for .xml, reads directly. Returns XmlPackage with byteBuffer, size, name. MainLoop creates XmlToken per package and pushes to parser.

10. Output & Flush Design Pattern

Per-entity PrintWriter writes to entityName_pending.txt. Flush occurs at fixed row intervals (originally 1000, tuned to 250 for this dataset). The batch count is global (flushBatchCount), not per writer — so all entities flush together when counter reaches threshold.

Technique: Global counter simplifies logic but couples all entities. If one entity writes far more data, it drives flush frequency for all. Per-entity counters would decouple, but add complexity.

12. How to Rebuild From This Document

If you have no source code, use this manual and the UserManual:

  1. Create xmlBluePrint class with FNV-1a hash, byte-level FSM, predictive log, and holder array.
  2. Implement pushJob(buffer, len, token) and pullJob() with pipeline slots = (2^N)-1.
  3. Add rootRegist(), errorRegist(), regist() using hash keys.
  4. Build BPParser that parses .bp into TokenEntity / TokenColumn map.
  5. Write SourceHandler scanning folder, opening .zip and .xml.
  6. Implement handler pattern (HD_Root, HD_Entity, HD_Column, HD_Error) registered with parser.
  7. Write MainLoop: fill pipeline, pull, flush (250 batch), reuse tokens.
  8. Write ClosingJob: close writers, rename pending, shutdown parser.
