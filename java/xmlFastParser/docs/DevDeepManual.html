Part I — The Hash (FNV-1a, Byte-by-Byte)

The parser does not use a library hash. It implements FNV-1a directly over raw bytes so it can skip prefixes and namespaces precisely.

Source — Exact Block (from xmlBluePrint.java)

public static final long hash(byte[] buff, int begin, int end) { // FNV_1a
  long h = 0xCBF29CE484222325L; // FNV offset basis

  // Find start of local name (skip prefix or Clark notation namespace)
  int hashStart = begin;
  for (int i = begin; i < end; i++) {
     byte v = buff[i];
     // Normalize to uppercase for case-insensitive matching
     if (v >= 'a' && v <= 'z') v = (byte)(v - 32);
     if (v == '}') {
        // Clark notation: {namespace}localName - start hashing after '}'
        hashStart = i + 1;
        break;
     }
  }

1

Offset basis. Every FNV-1a starts with 0xCBF29CE484222325. This is not arbitrary — it is the standard 64-bit offset basis for FNV-1a. Changing it breaks all existing hashes.

2

Find local name start. We scan from begin to end. If we see }, we know Clark notation {uri}local is used; we skip to after }. We also implicitly skip prefix before : because only bytes after the last prefix separator matter for local name.

3

Case normalization. Before using the byte, if it is lowercase a-z, subtract 32 (ASCII distance to uppercase). This makes /a/b and /A/B identical — the edit we made.

Why byte-level? The parser reads raw byte[] from XmlPackage. It never converts to String during parsing because that allocates objects and slows the loop. The hash operates directly on those bytes.

Part II — The Loop That Consumes Bytes

After finding hashStart, the loop continues hashing every byte through end using FNV-1a multiply+xor. This produces a 64-bit long that is used as a key in HashMap<Long, ...> for handler lookup.

Step-by-Step (Mental Model)

h = h ^ v;          // XOR byte into running hash
h = h * 0x100000001B3L;  // Multiply by FNV prime
// Repeat for each byte from hashStart to end

Never forget the prime. The prime 0x100000001B3L is part of FNV-1a. If you replace it with a different prime, you get a different hash family — all registrations break. The parser relies on consistent hash output.

Part III — Predictive Parsing (The Speed Trick)

Instead of scanning every byte from the start of a tag, the parser tries to jump to where it thinks the tag should be, based on previous patterns.

The Log

Inside the holder there is a predictedLog — essentially a history of tag hashes at positions. When parsing is active:





// Activation (simplified from source patterns)
bestMatch = findBestPredictedLogHolder();
if (bestMatch != null) {
  predictedIndex = bestMatch.bestIndex;
  predictedLog = bestMatch.log;
  predictionActive = true;
}

1

Log search. The parser looks at its history for the best match near current position.

2

Set index. predictedIndex points to which log entry to verify.

3

Jump. Pointer moves to predicted offset.

If It Works — Success

// Verification matches expected hash
holder.pointer = predictedOffset;  // jump succeeded
// Continue parsing from new position

If It Fails — Restore

// Hash mismatch at predicted location
originalPointer = holder.pointer;   // save before jump
// ... jump fails ...
holder.pointer = originalPointer;   // restore
predictionActive = false;          // disable for this segment

Why restore exactly to originalPointer? Because the parser may have partially advanced state (currentNode, skipDepth) during the jump attempt. Restoring pointer alone is not enough — but in the source pattern, the state is rebuilt after restoration because parsing restarts from the original byte sequence. The key insight is no partial state leaks.

Part IV — Pipeline Slot Reuse (Memory Efficiency)

Instead of allocating new XmlToken objects per file, the MainLoop reuses an array:







allXmlToken = new XmlToken[totalSizePipeLine];  // totalSizePipeLine = (2^N)-1
for (int i = 0; i < totalSizePipeLine; i++) {
  allXmlToken[i] = new XmlToken();  // allocate once
}

Then in loop:

// Pull completed token
XmlToken xmlToken = (XmlToken) parser.pullJob();
// Flush
flushXmlToken(xmlToken);
// Reuse with new XML
xmlToken.xml = xml;
parser.pushJob(xml.byteBuffer, xml.size, xmlToken);

Trick: By clearing buffOP and msgError after flush (not shown but implied), the same object can carry new data without garbage collection pressure. This is essential for processing 1,079,865 jobs (as observed in test).

Part V — Flush Arithmetic (Why 250?)

The flush is a global counter (flushBatchCount) incremented every record across all entities:

flushBatchCount++;
if (flushBatchCount % 250 == 0) {
  writer.flush();  // sync to disk
}

1

Every record writes. writer.println() buffers in memory; not all go to disk immediately.

2

Every 250: sync. flush() forces OS to write buffer to disk.

3

Sweet spot. 250 balances overhead (too frequent = syscall cost) with stall (too rare = parser waits for drain).

Measured result: 250 → ~274 sec (fastest); 50 → ~368 sec (too many syncs); 10,000 → ~358+ sec (stall). The disk rate balances near 200-300 row batches.

Part VI — ClosingJob Rename Sequence

After all output is written:

String timestamp = new SimpleDateFormat("yyyyMMddHHmmss").format(new Date());
for (TokenEntity entity : allTokenEntity.values()) {
  File oldFile = new File(destDir, entity.fileName + "_pending.txt");
  File newFile = new File(destDir, entity.fileName + "_" + timestamp + ".txt");
  if (oldFile.exists()) oldFile.renameTo(newFile);
}

Why _pending first? If program crashes mid-run, you still have partial output with a clear pending name. After successful close, rename gives final timestamped file — atomic-ish at OS level (rename is usually atomic on same filesystem).
