What is XMLFastReader?

XMLFastReader is a high-performance, multi-threaded XML parser for Java that prioritizes throughput and low latency over convenience. It's designed for scenarios where you process large volumes of structurally similar XML files and need maximum parsing speed with minimal GC pressure.

🎯 Primary Goal

Parse XML at near-memory-bandwidth speeds by eliminating all allocations, branches, and locks from the hot path.

Core Design Philosophy

Traditional ParsersXMLFastReader
Tree construction (DOM) or event streaming (SAX)Path-targeted callbacks — only what you register
Character-by-character with boundary checksByte-level table dispatch — O(1) array lookup
String allocation for every tokenZero-copy — offsets into original buffer
Single-threadedLock-free multi-threaded — ring buffers
Generic XML handlingSchema-aware optimization — knows your paths upfront
Error recovery, validationFail-fast — malformed = skip document
Trade-off: You must declare the XML paths you care about before parsing. In exchange, you get 5-50× speedup over SAX/DOM for targeted extraction.

Key Concepts

1. Byte-Level Finite State Machine

The Insight

XML is a regular language at the byte level. Every byte transitions between a finite set of states. Instead of if/else chains, use a transition table:

Traditional: Table-Driven (XMLFastReader): if (byte == '<') { TOC[currentState][byte].call(holder); if (next == '/') close(); // One array load + virtual call else if (isAlpha) open(); else error(); } else if (byte == '>') { // No branches, no allocations ... } // 20+ bytecodes/byte // ~5 bytecodes/byte

54 States

States encode context — are we in prologue? root? target content? attribute value? The state number itself is the "am I collecting data?" flag.

Target states (callbacks fire): Non-target states (structure only): S_TARGET_INNER (35) S_INNER (50) S_TARGET_ATTR (36) S_ATTR (49) S_VAL_ATTR (37) S_TAG_OPEN (48) S_QUOTE_VALUE (38) S_LT (41) S_DQUOTE_VALUE (39) S_BANG (42)... S_VAL_VALUE (40) S_UNREGIST_BRANCH (53)

2. Transition Table (TOC)

CELL[54][256] — One handler per state×byte combination.

Construction Strategy

  1. Default: All entries = HD_SAMESTATE (pointer++)
  2. UTF-8 Fast Path (all states):
    • 0xC0-0xDF → SKIP2_HANDLER
    • 0xE0-0xEF → SKIP3_HANDLER
    • 0xF0-0xF7 → SKIP4_HANDLER
  3. Per-state defaults
  4. Specific transitions
Multi-byte UTF-8 sequences are skipped entirely — continuation bytes never reach the state machine. This eliminates branching on high-bit bytes.

3. Hash-Based Path Matching

Why Hash?

  • O(1) lookup vs O(n) string compare
  • Fixed-size keys (64-bit) — no allocation
  • Namespace-agnostic: ns:Book → same hash as Book

FNV-1a + SplitMix64

long h = 0xCBF29CE484222325L;  // FNV offset basis
for (byte b : name) {
    if (b == ':' || b == '}') break;  // Strip namespace
    h ^= (b & 0xFF);
    h *= 0x100000001B3L;              // FNV prime
}
// SplitMix64 finalizer for avalanche
h ^= h >>> 33;
h *= 0xFF51AFD7ED558CCDL;
h ^= h >>> 33;
h *= 0xC4CEB9FE1A85EC53L;
h ^= h >>> 33;
return h;

Tree Structure

root (hash=0)
  └─ "catalog" (hash=H1, isTarget=false)
       └─ "book" (hash=H2, isTarget=false)
            └─ "author" (hash=H3, isTarget=true, handler, token)
            └─ "title"  (hash=H4, isTarget=true, handler, token)

Only leaf nodes (last segment of regist()) get handler/token and isTarget=true. Intermediate nodes are pure routing.

Paths start from first child of root: The registered path /catalog/book/author corresponds to XML .... The root element is handled separately via rootRegist() and is not included in the path.

4. Lock-Free Threading

Two-Level Ring Buffers

Global Queue (Blueprint, 16K): Producer → [job][job][job]... → Distributor Per-Holder Queue (Worker, 512 each): Distributor → [job][job]... → Worker Thread

No Locks — Only:

  • VarHandle.fullFence() — memory barrier after slot write
  • volatile pointers — visibility
  • LockSupport.park/unpark — thread parking

Thread Roles

ThreadRole
DistributorRound-robins global jobs to holders
Worker NOwns one holder; parses sequentially

Key Property

Blueprint is read-only after init. TOC, path tree, log store never change. Each holder is single-threaded — no internal synchronization needed.

Unregistered Branch Handling (No Depth Limit)

When the parser encounters elements not in registered paths, it enters skip mode:

  • Tracks the first unregistered tag name (by hash) + depth counter
  • On same tag name: depth++ (open) or depth-- (close)
  • When depth returns to 0: exits skip mode, resumes registered branch
  • No 32-level limit — depth is unbounded
  • No XML syntax validation in skipped branches — malformed content silently ignored
Guarantee: If the same unregistered tag name appears as both opening and closing (2nd/3rd occurrence), the parser will correctly unwind.

5. Predictive Shortcuts (Log-Based Acceleration)

Concept

Structurally similar XML files have similar byte-distance fingerprints between targets. Learn from past parses to skip FSM for non-target regions.

Structural Fingerprint

Log = [ (dist₀, hash₀), (dist₁, hash₁), ..., (distₙ, hashₙ) ]
      dist₀ = bytes from

Similarity Score

score = 0.7 × tagSequenceMatch + 0.3 × distanceRatioMatch

tagSequenceMatch = longestCommonPrefix / max(len)
distanceRatioMatch = avg(1 - |storedRatio - emergingRatio| / maxRatio)

Prediction Flow

  1. Parse document → build log → store in ring buffer (10K capacity)
  2. New document: after 1st target, query best-matching log
  3. Worker jumps to predictedOffset, peeks tag hash
  4. Match → skip FSM for jumped region
  5. Mismatch → fallback to normal FSM
Zero risk: Predictions are verified before use. Mismatch = immediate fallback. No correctness compromise.

When XMLFastReader Wins

  • Processing 10K+ XML files/hour
  • Extracting specific fields from large XML
  • Schema is stable (known paths upfront)
  • Multi-core hardware available
  • GC pauses must be minimized

When to Use XMLFastReader

✅ Ideal Use Cases

  • Log/Telemetry Processing: Millions of similar XML events
  • Data Ingestion Pipelines: ETL from XML feeds (finance, healthcare, IoT)
  • Message Bus Parsing: SOAP, FIXML, custom XML protocols
  • Batch XML Transformation: Convert XML → CSV/JSON/DB at scale
  • Monitoring/Alerting: Real-time XML stream analysis

❌ Not Ideal For

  • Ad-hoc XML exploration (unknown structure)
  • One-off parsing of small files
  • XPath queries on arbitrary paths
  • XML modification/round-trip
  • Schema validation required

Performance Trade-offs

  • First parse: No prediction benefit (cold start)
  • Dissimilar XML: Predictions disabled after mismatch
  • Small files: Thread overhead may dominate
  • Deep nesting: Unregistered branches track first tag name + depth (no 32-level limit); very deep same-tag nesting correctly handled
